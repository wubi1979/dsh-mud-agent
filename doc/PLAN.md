## 计划：T1 从「无状态渲染器」改为「有状态流程驱动器」

> 状态：**起草中**（2026-09-19 起）。本计划实施前不得据其改代码；实施后按本文件约定同步正式章节并删除本节。
> 未决项见本节末尾「未决」，其中**断线复位为最大未决，未定前不进入实施**。

### 背景与目标

现行 T1（§7）是**无状态动作渲染器**：动作由规则/流程声明并随投递消息送到，T1 只把 `source.actions` 渲染成 tool-call；流程状态归运行时（§19），两者靠 `flow.windowSpecFor` 把判据私塞给窗口、`noteToolResult` 事后推进（**配对移交**）来缝合。

该形态的直接症状：流程每一步都要一条投递消息（会话里表现为"上下文注入 / 助手 / 工具"三连），而注入的原文与上一步工具结果重复；且决策者实际有两个（运行时判据 + T1 渲染）。

**目标形态**：T1 = **有状态的流程管理器 + 输出渲染**。与 T2 的唯一区别是决策来源——T2 由 LLM 判断下一步，T1 依流程表判断下一步。二者同构：拿工具结果 → 决策 → 发下一个工具调用。

### 已定要点

**P1 入口**
- 流程入口经 **USER 注入投递**开回合，与 T2 同形（消息带原文 + `actions`；对规则动作它是"要做什么"，对流程入口它是"启动哪条流程 + 第一步"）。
- 入口投递**一律复位并重开流程**，不接续旧状态。
- 入口 arm 仍在会话侧（模型只在回合里活着，"流程该不该启动"必须有人在无回合时盯着行流）。这是流程内唯一必需的注入。

**P2 步内机制（骨架）**

```
T1(有状态，按 sessionId 分槽)
 ① 进入步骤 N：从流程表取本步 arming 集
 ② tool-call：命令 + 本步 arming 集（数据）
 ③ 工具：校验 → 凭据插值 → 写 socket
 ④ confirmSent 时刻 arm 标记到裁决器（带 owner = 本次调用/窗口）
 ⑤ 裁决器命中 → 当场切帧 → 取 span + 全部命中 → 按 owner 结算窗口
 ⑥ 工具返回 {span, hits[], captures, settled, ok}
 ⑦ T1 比对 → ok / fail / retry / 分支 → 更新槽值 → 回到 ② ；无路可走 → finish stop
```

**P3 注册时机**：T1 只供数据；**arm 必须由工具在 `confirmSent` 时执行**。若在 T1 决定发命令时就 arm，命令尚未写出，上一波残留输出即可命中标记，产生假边界。

**P4 arming 集范围**：**按步**注册（本步 driver(重试用) + 本步 ok/fail 判据 + 条件分支后继 driver），与 §19.2 现有口径同构；**不得**流程启动时全表注册（后续步判据会提前命中；I13 要求同一步 ok/fail 互斥）。

**P5 判据与边界**
- 接受"**判据当边界**"（省事且成立）；代价是只有写了判据的地方才切得干净，未写判据的命令落到 GA/超时。
- 多行判据**只在显式声明插话时**使用，与 §4 的多行写法约束一致。

**P6 span 与命中交付**
- span = **流程私有水位**（上次 span 结算推进到的行）→ 本批最后一次命中锚点（`consumeTo`）。
- 用**流程私有水位**，不复用 §5 的 `deliveredAbs`（后者会被折叠行/recall 前移，导致 span 空洞、多行判据失真）。
- 交付形态为 **`{span, hits[…], captures}`**：本批**全部命中按序**，不是只有触发那一条——否则"本步结果行 + 后继 driver 同帧到达"（§19.3 实录过的场景）会判错分支。

**P7 超时**：工具自带超时，到点直接返回 `{ok:false, settled:'timeout'}`；**不引入"继续等"路径**。超时是"放弃"语义（§8.4：帧不动、迟到内容随后照常提交），迟到内容会落进**下一次 span**，故流程表判据需容忍前置噪声。超时参数配错属配置问题，不由 T1 兜底。

**P8 失败分级**
- **步骤 fail**：表内有分支/重试 → T1 自己处理（决策者职责）；
- **流程失败**：无路可走 / 预算耗尽 → T1 `finish stop` 结束回合，**T2 从下一条投递接手**（已定方案 B，即回合结束后接手，不做回合内换手）。
- 需要**步数/时间预算 + 重试预算**，防 T1 高速空转（T1 是本地代码，循环不花钱）。

**P9 生命周期**
- 状态按 `sessionId` 分槽（该字段已在 mud-owned 消息的 `source` 里）。
- 复位是**被动**的：`callId` 配对不匹配（下一次调用等的结果不是自己发出的调用）或**连接代次**不匹配 → 弃用旧状态。不引入"回合取消钩子"（回合取消时 T1 不会被再叫，钩子也送不到）。
- **"流程活跃"绑定回合**（存在 lane=t1 的回合在跑且 T1 在该回合声明过流程）；**不引入 begin/end 声明**。这样回合结束活跃自动失效、入口 arm 自动恢复，即使 T1 漏报也不会僵死。
- 会话释放 = 重新初始化 → 清槽。
- **不引入"流程中途切 T2"**：`turnLane` 按回合锁定（`deliver/lane.ts`），同回合工具续步沿用本回合 lane，结构上不可能；唯一逃生口是用户取消回合。

**P10 硬约束（新增不变量候选）**
1. **流程的每一步都必须以"有界等待的工具调用"为承载体**——步的等待只能存在于工具内部（命令窗口 / 人工等待窗口），不允许"没有在途工具的干等步"（否则断线/无提示行时真正悬空）。
2. **凭据占位符 `{name}`/`{pass}` 必须原样传参**，由工具在发送瞬间插值；明文不落转录、日志、tool-call 参数。不因"T1 有状态"而把明文拿进 T1。
3. **流程表必须能从头重跑**（复位重开的隐含要求）。

**P11 运行时只读投影**：I10（单流程互斥 / 流程期间不 arm 其它入口）与 I14（`interrupts > priority`）所需信息从 T1 的 tool-call 参数投影到窗口注册；**运行时不得据此推进流程**（否则双权威复活）。

**P12 删除清单**

| 删除 | 原存在理由 |
|---|---|
| `flow.windowSpecFor` / `noteToolResult` 的流程部分 | 窗口与步骤的配对移交——T1 决策后不需要 |
| `syncArming()` 的流程 arming 重放 | 判据改由 T1 按步供给 |
| §19.6.2 判据 B 全套（`shouldConcludeTurn` / `deliverySizes` / `parseDeliveryCallId`） | 原为"工具结果携带 defer 投递时省一步空续步"；流程内不再有 defer 投递 |
| 流程步的 `deliver` + `deferContext` | 下一步动作由 T1 自己产出，不再需要投递消息作载体 |
| §5 对流程步的"投递消息携带原文" | 原文在 span 里，天然不缺 |
| 静态 `activityTable` 对**流程命令**的覆盖 | 流程内边界由流程表派生（静态表只服务非流程命令：T2 自发的、规则动作的） |

**P13 不变量与可测口径改写（候选）**
- 可测不变量：**`T1 消费的 span + T2 批次 + 折叠行 == 完整入站行流`**，替代 §5 现行的"按序拼接所有投递消息体 == 完整入站行流"。
- **I15**：由"T2 能接手流程中任意一步"改为"**流程外 T2 能接手；流程内 T1 的输入输出自描述**（tool-call 参数模型可读；工具结果只描述事实，不携带下一步指令）"。
- **I2**：措辞需同步——流程内的"下一步"不再经官方原语投递。
- 新增 P10-1 的"有界等待承载体"约束。

### 未决

| # | 事项 | 现状 / 初步想法 |
|---|---|---|
| U1 | **断线复位（最大未决）** | 目前机制不具备"流程整体挂起"能力（挂起需把流程状态 + 待发命令 + 人工等待 + 在途窗口序列化并在新连接按新行号重建，而重连后行号从 0 重起，锚点全失效）。**初步想法**：T1 设计"流程槽"；断线时服务器给出 EOF 标记，host 拿到标记后**开启新槽完成登录**。未定前不实施。 |
| U2 | 断线重连后默认复位重开 vs 尝试续接 | 倾向复位重开（简单可预测）；续接的风险：重连后服务器可能已把我们踢回登录前状态，续接会发出对不上号的命令。 |
| U3 | 流程私有水位与 `deliveredAbs` 的关系、折叠行是否进 span | 需定：流程期间水位由谁推进，避免 span 出现空洞。 |
| U4 | 超时后的迟到内容与下一次 span 的混合 | 需定流程表判据如何容忍前置噪声（现状固有性质，非新增风险）。 |
| U5 | 同帧多命中在裁决器侧的实现成本 | `{span, hits[]}` 的交付需要裁决器按 owner 汇总本批全部命中；现有 `consumeTo` 只给锚点位置。 |

### 验收（草案）

- 一个流程 = 一个回合、全程 T1；**回合内不出现投递消息**（除入口）。
- 会话形状为 `助手 / 工具` 交替，无逐步"上下文注入"。
- 登录 `replace` 分支在"本步结果行 + 后继 driver 同帧"场景下判定正确。
- 超时路径 → T1 按表决策（retry / fail / 分支），非"继续等"。
- 流程失败 → 回合结束，T2 从下一条投递接手。
