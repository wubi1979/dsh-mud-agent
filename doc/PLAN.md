## 计划：T1 从「无状态渲染器」改为「有状态流程驱动器」

**目标**：
- T1 从无状态动作渲染器改为有状态流程驱动器；流程回合内的"上下文注入 / 助手 / 工具"三件套消解为"入口投递 1 次 + 助手/工具交替"。
- 判据成为唯一结算器：GA 全域无缺省，收口来源三分（具体判据 / 显式 GA 声明 / 固定时长攒批），未声明直接报错。
- 行流守恒可测：每行恰好被消费一次，无折叠、无移交、无隐藏行。

**非目标**：
- 不做断线后流程挂起续接（已迁 §19.7 待定 #3，真实需求出现时再立项）。
- 不做多流程并行（T4）、不重估并发安全（T6）、不改分页与 halt 豁免策略（T7/T8）。
- 哨兵探测步（`set actioned` / `response actioned`）仅为实验功能，不进常规能力与验收。
- 多行判据仅作可选扩展预留，MVP 单行（§4"单行提示写成一条正则"约束保留）。

### 2. 背景与核心决策

**现行问题**：T1（§7）是**无状态动作渲染器**——动作由规则/流程声明并随投递消息送到，T1 只把 `source.actions` 渲染成 tool-call；流程状态归运行时（§19），两者靠 `flow.windowSpecFor` 配对移交判据、`noteToolResult` 事后推进来缝合。直接症状：流程每步一条投递消息（"上下文注入 / 助手 / 工具"三连，注入原文与上一步工具结果重复）；决策者有两个（运行时判据 + T1 渲染）。

**目标形态**：T1 = **有状态的流程驱动器 + 输出渲染**（按 sessionId 分槽）。与 T2 同构：拿工具结果 → 查表决策 → 发下一个 tool-call；唯一区别是决策来源——T2 由 LLM 判断，T1 依流程表判断。二者用同一套发送工具、同一结果形态。

**决策归并（D1–D8，括号内为原 P 编号）**：

**D1 入口**（原 P1 + #8）
- 流程入口经 **USER 注入投递**开回合，与 T2 同形（消息带原文 + `actions`；对规则动作它是"要做什么"，对流程入口它是"启动哪条流程 + 第一步"）。T1 保留两类回合职责：流程回合（状态机驱动）与动作渲染回合（规则动作渲染，无状态）。
- 入口投递**一律复位并重开流程**，不接续旧状态。
- 入口 arm 仍在会话侧（模型只在回合里活着，"流程该不该启动"必须有人在无回合时盯着行流）。这是流程内唯一必需的注入。
- **入口原文即触发行**：命中即消费，消费水位自然推进过该行；入口投递只引用已消费行，不重复消费行流。

**D2 步内机制**（原 P2 + P3 + #1 + #6）
- 六步循环：① 进入步骤 N，从流程表取判据集（fail / ok / 分支 driver 全显式）+ capture 规格 + timeoutMs → ② T1 组装阶段把命令 + 判据集 + captures + timeoutMs 写入 tool-call → ③ 工具：校验 → 凭据插值 → **confirmSent（注册判据进裁决器，owner = 本窗口；记录发送水位）→ 写 socket，两者之间零间隙** → ④ 裁决器结算（回看 / 实时 / 超时 / 打断）→ ⑤ 工具返回 `{settled, hit, span, captures}` → ⑥ T1 查表：更新槽值 → 下一步或收束。
- **工具缺省 = 固定时间攒批返回，无其他设置**；判据与超时只由 T1 组装写入（tool-call 参数）或规则/直发显式声明（规则表 / 活动表条目）提供。
- **无任何"结算后等行"状态**：窗口只在判据命中 / 超时 / 打断 / 断线时结算，步的等待全部在工具内部。

**D3 判据与结算**（原 P4 + P5 + P6 + #1 + #2）
- 判据集**按步**随 tool-call 供给，**全显式**；空类 = 该类不命中、跳过（不是整体失败）。**不得**流程启动时全表注册（后续步判据会提前命中）。
- 判定顺序：**fail → 分支 → ok**（同帧多类命中按此序取一，其余留痕；与 login `replace` 分支同帧实录一致）。
- **GA 全域无缺省**：收口来源只有三种——具体判据、显式 GA 声明（`ok:[GA]`，N-GA 为其参数）、T2 自发固定时长攒批。**未声明判据且未显式声明 GA → 直接报错**（装配期校验流程表/规则表，调用期校验工具参数），不回落任何缺省。规则动作 = 显式声明（载体为规则表 / 活动表条目；活动表从"N-GA 缺省 + 判据命中结算"重定义为"规则 / 直发命令的显式判据声明载体"）。
- **发送水位与回看**：confirmSent 记录发送水位（当时行流头位置）；**裁决器可按发送水位以下未消费行结算（回看）**——"本步结果行 + 后继 driver 同帧"场景由此承接，旧 §19.2"后继 driver 一起 arm"的动因在新模型下由回看消化。
- span = **消费水位 → 触发行（含）**，不复用 §5 的 `deliveredAbs`；触发行之后的同帧行、GA、迟到行落后续消费区间作前置噪声。**非空结算约束**：命中结算的 span 至少含触发行一行（GA 行计入），禁止空值结算；超时且零行 = 无应答事实，留痕收束，不产出空 span。
- **状态抓取为独立桶**：抓取结果**只同步 world**；**不驱动水位、不折叠内容**——状态行作为普通行被后续 span/批次包含，行流无隐藏行（#2 取代原 U3"折叠但不推进水位、不进 span"口径）。
- capture 规格（槽名: 正则）随判据集注册，触发命中经回调把抽取值送回工具 → 工具结果 `captures` → T1 存槽。占位符三类通道：`{name}`/`{pass}` 原样传参、工具经凭据 seam 发送瞬间插值（明文不落转录/日志/tool-call 参数）；`{captcha}` 工具内部闭环；capture 槽 / `{lastFail}` 由 T1 组装时直写值。
- 判据是唯一结算器 ⇒ **误命中 = 误结算**：判据特异性是流程表编写纪律，装配期做特异性告警。

**D4 超时与失败**（原 P7 + P8 + #3）
- **超时不做最后判定**：超时即**提交全部窗口内容**（消费水位 → 缓冲头），**记为当前调用者消费**（水位推进到缓冲头），无兜底判定；随后流程失败收束。超时不进 retry（retry 仅由 fail 判据驱动）。
- **T2 不接受移交**：T2 批次永远从缓冲**自行回看**（自消费水位起），不接收流程侧移交内容（原"超时窗口内容自然移交给 T2"口径废除）。
- **步骤 fail**（判据命中 fail 类）→ 表内分支 / 重试（决策者职责）；fail 命中且无重试/分支 → 流程失败。
- **流程失败**（超时 / fail 无出口 / 预算耗尽）→ 留痕 → 复位 → T1 `finish stop` 结束回合，**T2 从下一条投递接手**（回合结束后接手，不做回合内换手）。
- **流程失败的未结算行不丢弃、不移交**：留在缓冲，作为下一批入口原文（入口 driver 命中）或 T2 批次被消费（#8）。
- 预算：步数 / 时间 / 重试预算防 T1 高速空转（timeoutMs / retry.attempts 已有，步数预算为流程级新增）。

**D5 打断与排队**（原 P8 打断部分）
- **打断**：在途窗口结算 `interrupted` → **直接收束流程槽**（复位 + 留痕），**不进 retry/fail 分支、不走 failPolicy**；事件动作经 **followup 新回合**投递（不在同回合 defer，defer 面全删）。I14 语义不变："可打断立即执行"变为"下一回合立即"，排队语义不变。
- **结算优先级：打断 > 判据命中 > 超时 > 断线**；打断与判据同帧时打断优先，判据命中作废留痕。

**D6 生命周期**（原 P9）
- 状态按 `sessionId` 分槽（字段已在 mud-owned 消息的 `source` 里）。
- 复位是**被动**的：`callId` 配对不匹配或**连接代次**不匹配 → 弃用旧状态。不引入"回合取消钩子"（在途工具经 `exec.signal` 立即返回 canceled）。
- **断线口径 = 复位重开**：重连后入口 driver 重新命中 → 入口投递重开流程。
- **"流程活跃"绑定回合**：回合结束 → 活跃自动失效 → 入口 arm 恢复 + `drainFlowQueue` 出队（接线点：回合结束事件 / finish 钩子，S4 定）。不引入 begin/end 声明。
- **I10 预激活**：入口投递本身即互斥信号；`awaitExternal` / 人工窗口（humanWindow）同样携带 priority 投影。会话释放 = 重新初始化 → 清槽。
- **不引入"流程中途切 T2"**：`turnLane` 按回合锁定，同回合工具续步沿用本回合 lane，结构上不可能；唯一逃生口是用户取消回合。

**D7 硬约束**（原 P10）
1. **步的等待只能存在于工具内部**（命令窗口 / 人工等待窗口）——判据-only 收口下自动满足，不允许"没有在途工具的干等步"。
2. **凭据占位符 `{name}`/`{pass}` 必须原样传参**，由工具在发送瞬间插值；明文不落转录、日志、tool-call 参数。
3. **流程表必须能从头重跑**（复位重开的隐含要求）。

**D8 运行时只读投影**（原 P11）
- I10（单流程互斥 / 流程期间不 arm 其它入口，含入口投递预激活）与 I14（`interrupts > priority`）所需信息从 T1 的 tool-call 参数 / 入口投递投影到窗口注册；**运行时不得据此推进流程**（否则双权威复活）。

### 3. 机制与契约

#### 3.1 tool-call 参数契约（T1 → 发送工具）

```
mud_send {
  cmd: string                    // 命令行；占位符按三类通道处理（D3）
  criteria?: {                   // T1 流程步组装写入
    ok?: MatchSpec[]             // 成功判据（可含显式 GA kind）
    fail?: MatchSpec[]           // 失败判据
    branch?: { id, match }[]     // 条件分支 driver
    ga?: { count: N, on: 'ok'|'fail' }  // 显式 GA 声明（语法定稿见第 6 章）
  }
  captures?: { 槽名: 正则 }       // 随判据注册，命中经回调回送
  timeoutMs?: number             // T1 流程步必填；T2 缺省攒批模式不传
}
```

- **判据来源解析（工具侧，按序）**：① tool-call 参数（T1 流程步）→ ② 命令的显式声明（规则表 / 活动表条目，规则动作与直发命令）→ ③ 都无：**T2 lane = 固定时长攒批（缺省）**；**T1 lane = error**（未声明收口，#6/#8 校验）。
- T1 / T2 使用相同工具、相同结果形态（既有口径不变）。

#### 3.2 工具返回契约

```
{ settled: 'hit' | 'timeout' | 'interrupted' | 'canceled',
  hit?: { class: 'ok' | 'fail' | 'branch', id? },   // settled='hit' 时必有
  span?: { fromAbs, toAbs },                         // 消费水位 → 触发行 / 提交点（留痕 / 审计 / 自描述）
  captures?: { 槽名: 值 } }
```

- `hit` → T1 查表推进；`timeout` → 内容已提交并记当前调用者消费，T1 收束流程；`interrupted` → T1 收束流程槽；`canceled` → 回合取消（槽被动复位）。
- **判定以 hit 为准**：T1 信任工具判定，不重复匹配；span 供留痕 / 审计 / 自描述。

#### 3.3 流程表（口径增补）

Schema 沿 §19.1 骨架，增补：判据全显式（ok / fail / 分支至少其一，或显式 GA；空类 = 跳过）；`timeoutMs` 步级必填（装配期校验）；`GA` 仅为显式判据 kind（ok/fail 同写 GA → 降为告警 + 同帧按 fail→分支→ok 定序，I13 改写）；步数预算为流程级新字段；多行判据 MVP 不支持。新 schema 定稿见第 6 章（实现待定）。

#### 3.4 T1 槽结构（按 sessionId 分槽）

`flowId` / `stepId` / `captureSlots` / `lastFail` / `attemptCounts` / `stepBudget` / `connectionGen` / `lane`。结构定稿见第 6 章。

#### 3.5 裁决器（`SessionAdjudicator` 增量）

- **判据 owner 化挂窗口**：confirmSent 时注册（owner = 在途窗口）；帧提交匹配命中 → 结算该窗口。
- **发送水位**：confirmSent 时刻的行流头位置，随窗口记录；confirmSent → 写 socket 零间隙。
- **回看结算**：注册时对（消费水位, 发送水位] 的未消费行匹配一次，命中即结算（命令照常写出；发送无条件，结算只决定结果报告时机）。
- **结算产出**：span（消费水位 → 触发行，含）+ capture 回调回送 + 消费水位推进到触发行。
- **结算优先级**：打断 > 判据（含回看） > 超时 > 断线；同帧多类命中按 fail → 分支 → ok 取一，其余留痕。

#### 3.6 状态抓取桶

- 声明载体：state 规则（§4 trigger）照旧；命中动作改为"抽取 → **同步 world**"，仅此一个效果。
- **不驱动水位、不折叠内容**：状态行保留在行流中，作为普通行被后续 span/批次原样包含；行流无隐藏行。
- 与 §5 现行差异：现行折叠消费会隐藏行并前移 `deliveredAbs`（span 空洞、多行判据失真的动因）；新口径下该机制整体删除。

#### 3.7 两个水位

- **消费水位（每会话一条）**：行流消费进度。推进来源：判据命中（→ 触发行）、超时/打断提交（→ 缓冲头，记当前调用者消费；打断口径缺省留痕消费，见第 6 章）、T2 攒批收口（→ 缓冲头）、入口/规则命中行（→ 命中行）。
- **发送水位（每窗口一条）**：confirmSent 时刻的行流头；仅作回看区间上界与审计，不推进、不消费。
- 原则：**行流只有"消费水位"一条真相**；`deliveredAbs` 的折叠/recall 前移口径废除。

#### 3.8 状态机与时序

T1 槽状态机：

```
idle ──入口投递（复位重开）──> running(step N)
running: 组装 tool-call → await 工具结果
  ├─ hit ok      → next（顺序兜底 / 终态）；终态 = onSuccess → finish stop → idle
  ├─ hit branch  → 进入分支步 → running(step M)
  ├─ hit fail    → retry（次数内，重投本步动作，计时器不重置）？ 流程失败
  ├─ timeout     → 内容已提交消费 → 流程失败
  ├─ interrupted → 收束复位 → idle（事件动作走 followup 新回合）
  └─ canceled    → 槽保留，被动复位（callId / 连接代次不匹配时弃用）
流程失败 → 留痕 → 复位 → finish stop → idle（T2 从下一条投递接手）
回合结束 → 活跃失效 → idle（入口 arm 恢复 + drainFlowQueue 出队）
```

一步时序：

```
T1 查表进入步骤 N
  → 组装 tool-call（cmd + 判据集 + captures + timeoutMs）        [#6 组装阶段写入]
工具：
  校验（判据来源解析三序，T1 lane 缺声明 → error）
  → 凭据插值（{name}/{pass} seam，发送瞬间）
  → confirmSent：注册判据（owner=窗口）+ 记发送水位 + 回看匹配（命中即结算）  [#1]
  → 写 socket（与 confirmSent 零间隙）                            [#1]
  → 等待：实时行匹配 / 超时提交 / 打断 / canceled
  → 返回 {settled, hit, span, captures}
T1：hit → 查表（fail → 分支 → ok 已由裁决器定序取一）→ 更新槽 → 下一步 / 收束
```

#### 3.9 配置、默认值与校验

- **装配期校验（fail loud）**：流程表——判据全显式 / 未声明收口报错、ok/fail 互斥 → 告警、timeoutMs 必填、判据特异性告警、next 引用存在、占位符三类、capture 槽名唯一；规则表 / 活动表——规则 / 直发命令显式判据声明，未声明报错。
- **调用期校验**：T1 lane 缺判据声明 → error；capture 正则编译失败 → error。
- 配置项与默认值（T2 攒批时长、timeoutMs 全局缺省、步数/重试预算）见第 6 章（数值待校准）。

#### 3.10 行流唯一归属与不变量

- **每行恰好被消费一次**。消费者枚举：① 规则 / 入口 / 判据命中行（匹配即消费，#8 入口原文已触发、水位自然推进）② 流程 span（含超时/打断提交区间）③ T2 批次 ④ 仍带原文的投递（原文行未被 ①–③ 覆盖时，如排队出队 pendingEntry）。
- 无折叠：行流无隐藏行；状态抓取不消费行（只观察 + 同步 world）。
- 流程失败未结算行：留在缓冲，作为下一批入口原文或 T2 批次被消费（不丢弃、不移交，#8）。
- **可测不变量**：`① + ② + ③ + ④ == 完整入站行流`（替代 §5 现行"按序拼接投递消息体"口径；折叠类目移除）。pendingEntry 的行流归属沿 §19.7 待定（T5），不在本计划内定。

## 语义级缺口（建议起草期定案，不只是“数值待校准”）
1. T2 自发调用的攒批与 GA 的关系未定 D2 说“工具缺省 = 固定时间攒批返回，无其他设置”。但现行`mud_look` /`mud_status` 等窗口型查询是 GA 关窗即返回（ inflight.ts`boundary()` ）。新模型下这些工具无判据声明 → 落攒批。若攒批不允许 GA 提前收口，查询工具响应延迟明显回退；若允许 GA 提前收口，GA 又成了缺省收口器，与“GA 全域无缺省”直接冲突。计划第 6 章只把攒批时长列为“数值待校准”，但这是 语义 问题（固定窗 / 静默窗 / GA 提前收口三选一），不是数值问题。

2. mud_recall 与交付水位的去向 §3.7 说“`deliveredAbs` 的折叠/recall 前移口径废除”，但 adjudicator.ts 的`recall()` /`noteDelivered()` 整个机制依赖交付水位区分“模型看过的行”。计划源码变更清单（第 4 章）没有提 recall 面的处理。消费水位 ≠ 交付水位（消费含 span/命中行，交付含投递消息），二者混一后 recall 的“尚未投递给你”语义需要重新定义。

3. 消费水位的物理载体未指认 现有行流有 两级缓冲 ：`FrameSplitter.open` （开放帧，未提交）与`SessionAdjudicator.pending` （已提交帧、待投递，被 T2 限流/人工环节压着）。§3.7 的“缓冲头”指哪一级？§3.5 回看区间 (消费水位， 发送水位] 的匹配数据源是否含待决缓冲？现行`arm()` 的“arming 即测”只扫开放帧（ adjudicator.ts ）。若回看把 pending 行也算进来，这些行上 已经发生过的规则命中/折叠 会不会构成双消费，与 §3.10“每行恰好消费一次”冲突，需要给判据。

4. 打断 followup 新回合的触发点完全没写 D5 说打断后事件动作“经 followup 新回合投递（defer 面全删）”。现行打断路径是：`admitRuleHits` →`flow.interrupt()` 同步复位 → 窗口结算 interrupted → 事件动作走 defer 槽随工具结果进同一回合。改 followup 后：谁在什么时点调 followup（官方 exec 的哪个 API）？打断时被中断工具还没返回、T1 槽还没收束（收束要等工具结果回到 T1），这个异步间隙里 I10 互斥与“流程活跃绑定回合”（D6）以什么时点翻转？计划把 defer 判据 A/B 列入删除是对的，但新载体（followup）的接线点应像 D6 的 drainFlowQueue 一样被明确标为待定项。

## 契约级含糊（S1/S2 需覆盖，建议计划点名）
5. 流程回合与动作渲染回合的区分面 现行 T1 靠`turnContext` 尾扫 mud-owned 消息 + 确定性 call-id（ t1.ts ）。新模型下同一个 provider 要承载两类回合（流程状态机驱动 / 规则动作无状态渲染），计划 §3.4 有槽结构但没定义：入口投递消息“启动哪条流程 + 第一步”的字段形状；T1 查表推进时工具结果与步骤的关联（callId ↔ 槽内当前步 callId）；turnLane 按回合锁定后 lane 值如何区分两类回合。 I15（`source.actions` 模型可见）在新形态下是否保留、保留到什么程度 ，直接影响验收怎么写。

6. 直发命令与纯工具步的收口声明豁免 §3.9 说“规则/直发命令未声明收口报错”。但 direct-exec 现在是“发完即走、不等应答”（ adjudicator.ts ），根本没有收口可言——校验对象是什么？同理，`mud_captcha` /fullme 解析步这类不经过在途窗口的纯工具步，现行靠`FlowMatch kind:'tool'` 判定（ flow-spec.ts ），而新 criteria schema（§3.1 只有 ok/fail/branch/ga）里没有 tool 类——这类步是“工具返回即收口”自动豁免，还是必须另立声明形式？fullme 表重写（W10.1）会直接撞上。

7. 入口投递“复位重开”与 I10 互斥的共存 流程活跃期间入口不 arm、其它入口行进 pendingEntry 排队（ flow/engine.ts ）。那么“入口投递一律复位并重开”实际只可能作用于：pendingEntry 出队投递、重连后重新命中。 pendingEntry 出队算不算“入口投递”、走不走复位重开 需要点名；否则 D1 与 D6 互斥口径在边缘场景互相矛盾。
