# §6 L4 通路层：三条通道与接入闸门

## 6.1 通道全景

| 通道 | 方向 | 载体 | 受接入闸门？ | 权威章节 |
|---|---|---|---|---|
| **投递通道** | MUD → agent | 会话**用户消息**（`kind: 'mud'`）触发宿主回合 | ✅ **唯一受闸门的通路** | §6.2、§6.3 |
| **显示通道** | MUD → 人 | `follow` 画面帧 / `watchStatus` 状态帧 / `logs` 日志 | ❌（人是旁观者，不消耗 agent 预算） | §6.4 |
| **发送通道** | agent → MUD | 工具 `mud_send` / 流程 `mud_workflow_run` | ❌（**只拒未连接**；应答经工具结果返回调用方） | §6.5 |

> 通道的划分是**架构级裁定**：闸门定义在**通路集合**上，任何新通路落地都必须先回答"它受不受闸门约束"（P5）。

## 6.2 MUD→agent 投递通道

**通路 = 会话消息投递**（与人工提问**同一通道**）：

```
MUD 行流 → 聚合（静默窗口，§5.4）→ 一条用户消息投递进该账号的会话
        → 宿主原生回合机制（followup 排队 / steer 步边界插话——与 session/prompt 同路）
        → agent 开回合，产生回答（回答落会话，页面可见）
```

- **等同人工提问**：MUD 信息以**用户消息**身份进入会话并触发回合，agent 像被提问一样回答。
  - 已弃用方案：原"LLM 调用监听钩子注入"只能改已有调用的上下文、**不产生回答**，与目标不符；其拦截角色也不再需要（第一期唯一通路就是投递通道，闸门在源头）。
- **聚合是必需品不是优化**：逐行投递 = 每行一个回合一次模型调用；空闲模式按静默窗口聚合（§5.4 参数）。
- **署名区分来源**：行批次 `kind: 'mud'`；任务书/唤醒 `kind: 'mud-wake'`（两者都是"非用户的插件消息"，但语义不同，§7.4）。
- **与人工提问共存**：投递走宿主 followup 队列，**人工消息与 MUD 消息同队列自然排队**（会话内串行是宿主保证）。
- **回答的去向**：回答落会话（页面可见、日志可查）；**回流 MUD 的唯一通道 = `mud_send` 工具**（§6.5）——投递通道本身**单向**（MUD→agent），回答不自动回流。
- **按会话隔离**：每个 runtime 只向自己的会话投递（两会话互不串线）。
- **失败不丢行**：投递回调返回 `false`（agent 离线 / `followup` 抛错）⇒ 批次不推进 `deliveredAbs`，等 `agent/created` 的 `flushPending` 补投（P7）。

## 6.3 接入闸门

**接入 = 独立手工开关**（`admit`/`stop`，roster `accounts.admitted` **持久**、缺省**未接入**）。

| 动作 | 语义 |
|---|---|
| **接入 admit** | 投递通道开；**水位 = 接入时刻，不回放积压**（接入前的行流不投；要看近况用 `mud_send` 裸读，§5.2）。admit 同时投一条**状态任务书**触发规划（两动作合一，保持 admit 纯闸门语义，§7.4） |
| **停止接入 stop** | **MUD 信息不再进入 agent**：投递停（**在途回合自然跑完**，后续零投递）；行流照常积累 = **录制**；**已投递的历史留在会话里不动** |
| **未接入（缺省）** | **零进入**：不 take、不武装定时器、零缓冲零丢弃（§4.5）。agent 诚实答"我未接入 MUD" |
| **人工提问** | **不受闸门影响**：人工在会话里发消息是宿主原生回合，不拦 |
| **新通路** | **后续任何新通路一律受本闸门约束**（现在定死，防止机制生长时语义漂移）：唤醒类机制落地必须以"已接入"为前置 |
| **例外（三期修订）** | `mud_send` 不受闸门（只拒未连接）——应答经工具结果返回**调用方**，不是投递通路（§6.5） |

- **与 `connect` 正交**：`connect` 管 MUD 源（socket），**接入**管 MUD→agent 的信息流。
- **与上下文收口解耦（T18）**：冷启动恢复的旧会话在本进程**第一次 model step 之前**被遮蔽（§11.2）——遮蔽**不依赖接入**（未接入会话同样先清理），`admit` 语义与"水位 = 接入时刻"不变；遮蔽失败会让该步被 reject（回合 `blocked`、无模型调用）。
- **有标行剔除（C5.2，2026-10-03）**：`MudLine.kind` 由分类器在 runtime 行路径单点写入（全系统唯一一次**分类**），有标行（如聊天）**不进投递**——安全前提「聊天不进 agent」在投递侧落地；白名单 `allowKinds` 可放行特定 kind，有标行视为已见（水位越过）。**T19 追踪打标是第二个写入点**（非分类）：状态追踪器（§10.3）在同一行路径、分类器之后 `observe`，只对 `kind === null` 的行补打 `status`（剔除噪声表格），**不覆盖分类结果**（C5.2 规则优先）。
- **规则族（2026-10-03 + 2026-10-06 实录校准）**：`chat`（行首 `【频道】`）· `action`（他人动作/进出/离场/**穿戴装备**/**给与**，主语非你）· `vitals`（他人状态/调息/疗伤刷屏，主语非你）；**自身行（`你…`）一律保留主屏**（自身状态与警告 agent 需据此行动，2026-10-03 用户裁定）。2026-10-06 用户实录补 `X戴上一件…。` / `X给Y一把…` / `X快步离开，…。` / `X默默提气，…` 四类漏网，并以**全量回放**（`logs/` 全部 `[stream]` 行，2212 行）逐条收紧：命中 1073 行（`action` 858 / `vitals` 189 / `chat` 26），剩余未打标且形态可疑者由 62 行降到 **11 行且全部为应当保留**（登录成功判据「重新连线完毕。」、重复连线提示、`你…` 自身提示、本人记录边框）；误报审计（命中行含「你」或以描述词开头）**9 条全部为他人动作**（`一个书生…踱了过来。`）⇒ 零误报。
- **"连接 + 未接入" = 录制/挂机模式**（连着收流、角色在线、agent 零 MUD 行为）——语料采集、登录调试、离开时省 token 的形态。嫌两步麻烦可在管理面做组合按钮，**底层动词仍是两个**。

## 6.4 MUD→人 显示通道（不经闸门）

三条只读出口，**都不产生"行进入 agent"**：

1. **画面 `follow`**（§5.3）：无头屏 snapshot + 增量帧；未接入也可看（显示面不经闸门，agent 零进入语义不变）。
2. **状态 `watchStatus`**（§9.5）：首帧全量快照，之后仅变化推帧；客户端 abort 即清服务端订阅。
3. **日志 `logs`**（§13.2）：该会话日志环条目 + 落盘目录。

> 纪律：显示通道**纯扇出、无输入**；tab 关闭 = follower 清理，连接与投递不受影响（§5.3）。

## 6.5 agent→MUD 发送通道

| 入口 | 语义 | 与闸门关系 |
|---|---|---|
| `mud_send`（工具） | 发命令 + 判据驱动等应答；不带 `cmd` = 裸读近况 | **不受闸门**，只拒未连接（应答返回调用方） |
| `mud_connect`（工具） | 幂等建连 | 无关（连接层） |
| `mud_workflow_run`（流程） | 白名单执行声明式流程（含 `sendCredential`） | **不受闸门**；有持有者独占约束（§8.6） |

- 发送通道的**硬约束**：同一时刻只允许一个执行体在 send+read（会话级持有者，§8.6）；禁发表拦截位于发送前（§8.4）；凭据动词只允许 locked 流程（§8.12）。
- 发送会写画面回显（账号名@来源），但**凭据不回显**（§5.3、§12.2）。

## 6.6 正交性表

| 状态组合 | `connect` | `admit` | MUD→agent | MUD→人 | agent→MUD | 用途 |
|---|---|---|---|---|---|---|
| 未连接 + 未接入 | — | — | 零 | 零（无流） | 工具可读拒绝"未连接" | 初始态（建账号后） |
| 已连接 + 未接入 | ✅ | — | **零** | ✅ 画面/日志 | ✅（手工/工具） | **录制 / 挂机 / 登录调试** |
| 已连接 + 已接入 | ✅ | ✅ | **投递** | ✅ | ✅ | 正常运行 |
| 已连接 + 已停止接入 | ✅ | ✅→stop | **零**（历史留在会话） | ✅ | ✅ | 暂停 agent 参与、保留观察 |
| 断线（任意） | — | 保持 | 零（`pendingLines` 清空） | 画面保留旧屏 | 可读拒绝 | 等手工重连（§11.3） |

**人工提问在任意组合下都可用**（不受闸门、不受连接状态影响）。

# §7 L5 agent 层：装配、回合与自主行为

## 7.1 preset 装配与 persona

- **能力面由 preset 决定**：`mud-player` preset 行 = 宿主 `standard` 的插件面 + MUD persona + **本包 preset 行**（引擎 `mud-core3`）+ **`mud-workflow` 行**（流程七工具）。**建账号时显式传 `agentPreset`**，**不覆盖** registry 默认。
- 账号可选 `standard`/`mud-player`：**选 `standard` 的账号没有 MUD 工具**（agent 只能接消息、不能发命令）——这是使用者的显式选择，不是缺陷；归属不按 preset 排除（§1.4）。
- **persona 是书写约定、无代码解析**，包含三块：
  1. **玩家身份**与最小行为纪律；
  2. **工具说明**（`mud_connect`/`mud_send`/`mud_state`/流程工具）与"**MUD 消息以用户消息到达，直接回答**";
  3. **分工协议五条**（根/子同读、按角色行事，§7.6）。
- 工具挂 **preset 作用域**：注册期不依赖引擎，执行期 `ctx.get('mudCore3')` 解析引擎窄面；注册完整性自检 fail-loud（§8.1）。

## 7.2 回合节拍与投递时机

| 宿主事件 | 本层动作 |
|---|---|
| `turn/start` | **抑制模式**：投递器不武装定时器，行只进 `pendingLines`（不打断回合节奏） |
| `turn/end` | **冲刷一次**：回合内积累的行一次投出（订阅 `session/event` global）。**必须推迟一个微任务**：该观察者处于宿主 `Session.append` 的发布期内，而发布期内禁止重入追加（`session append cannot reenter while another append is being published`），同步冲刷会经 `followup` 追加 `user/message` 而被护栏拒绝（症状：投递报错、该批行延后一回合补投） |
| （空闲） | 静默定时语义保留：`quietMs` / `maxWaitMs` 到期即 flush |
| `agent/created` | `flushPending`：把冷会话期间保留的批次投出（触发首个回合） |

完整水位语义见 §4.3。

## 7.3 会话生命周期接线

```ts
// index.ts（宿主装配）
agent/created   → roster 判定（sessionId ∈ accounts）→ service.register（幂等）
                → 记录 agent 句柄（投递出口）→ 装每会话 Wake（§7.5）→ flushPending 补投
agent/disposed  → 移除 agent 句柄（runtime / deliverer / 连接保留）
session/disposed→ 拆 Wake + 断连 + 拆 runtime / deliverer / 日志 + 清 agent 句柄
session/event   → turn/start 抑制 / turn/end 冲刷（§7.2）
插件卸载        → 拆全部 Wake + disposeAll
```

- **归属解析同一路径**：`runtimeFor(agent)` / `toolContextFor(agent)` 都查 roster 归属（§15.2）；归属上溯见 §8.5。
- **冷会话保留**：宿主释放 agent 不拆 runtime 与连接（§3.2）。

## 7.4 任务书面（kickoff）

**两触发点共用同一 `kickoff(sessionId)` 与同一模板**（建账号触发点已退役，2026-10-02 裁定：建账号 = 纯登记，**不投任务书**、会话保持 blank、agent 零行动；接入 = 唯一任务书点火点）：

| 触发点 | 语义 |
|---|---|
| ① **admit** | 经 `MudServiceDeps.onAdmit` 回调注入：**开闸门并投一条状态任务书触发规划**，两动作合一；同步先置 `admitted` 再点火，LLM 闸门时序上必放行 |
| ② **静默唤醒到期** | Wake 命中后投状态任务书（§7.5；守卫 ① 已含「已接入」） |

- **正文 = 状态驱动**：服务器/账号事实 + 两轴实时状态 + 目标——**只给事实与目标，不写指令序列**（根醒来读状态自行规划，已完成的步骤不重做）。
- **模板 = Config `taskBrief`**：占位符 `{{serverName}}` / `{{endpoint}}` / `{{account}}` / `{{conn}}` / `{{loggedIn}}`，投递时以**实时状态**填充；缺省内置 `DEFAULT_TASK_BRIEF`，部署可覆盖。
- **署名 `'mud-wake'`**（声明合并自扩），与行批次 `'mud'` 区分。
- **不该触发的情形**：admit 之前的**手工「连接」不触发规划**（手动连接 = 调试用途）；已接入场景下断线后的补登录由**静默唤醒兜底**（`mud_connect` 幂等，不负责重连）。
- 投递失败**不影响账号落库**（账号注册与开场消息解耦）。
- **与进程起点标记的分工（T18）**：冷启动后本进程首次 model step 前会追一条 `'mud-epoch'` 署名的**进程起点标记**（§11.2），它只声明"上一进程的历史已失效"，**不代替任务书**——事实与目标仍由任务书给；两触发点（接入 / 静默唤醒）一律不变。

## 7.4.1 LLM 调用面闸门（`llm/stream` 瀑布终审）

模型调用面的准入终审（2026-10-02）：宿主 `LlmRuntime.stream()` 走 cordis 瀑布 `llm/stream`（监听器不调 `next()` 即否决，官方契约），且 `GenerateOptions.sessionId` 由 loop 盖会话身份戳——闸门按 session 精确作用域（判定在纯层 `llm-gate.ts`：非本插件会话放行；本插件会话 fail-closed，投递器缺席 = 未接入）。

| 场景 | 行为 |
|---|---|
| 未接入账号会话的任何模型调用 | 拦成**空 stop 流**（单条 `finish: stop` 终块，0 token、无内容块）；`turn/start` 已发 → blank 照翻，回合自然收束 |
| 停止接入后进行中的回合 | 下一步 LLM 调用处空步收束：在飞工具正常完成、无 cancelled 残迹（**不 cancel、不打断**） |
| 人工提问（未接入） | 同样被拦——未接入 = agent 完全惰性（建账号纯登记后 blank 无驱动源，钩子兜住一切泄漏路径） |
| 已接入 | 放行（admit 同步先置位再点火） |

与投递面闸门（§6.3）+ 静默唤醒三守卫（§7.5）构成**三重防线**；监听器注册在插件 fiber，卸载自拆。

## 7.5 静默唤醒器（Wake）

每会话一实例（`agent/created` 装、`session/disposed` 与插件卸载拆）。

- **单 timer + 行到达即 re-arm**（`runtime.onActivity`）：行流持续到达**永不到期**；静默满 `silenceMs`（Config，缺省 **120_000**，正整数 fail-loud）后到期检查**三守卫**：

| # | 守卫 | 理由 |
|---|---|---|
| ① | **已接入** | §6.3 闸门前置：唤醒以"已接入"为前置 |
| ② | **非回合中** | 回合中开新回合会打断节奏（turn/end 后的持续静默会再次到期） |
| ③ | **行流持有者空闲**（无在途 read/send） | 在途 read 有自己的收束，不该被唤醒抢占 |

- 任一守卫不满足 ⇒ **只 re-arm、不唤醒**；三守卫全过 ⇒ `kickoff` 投状态任务书。
- **fire 后不自动重复**，靠后续行到达重新武装。
- **不做**"无子 agent 在途"守卫（V7 纪律）：**接受冗余唤醒**——根的决策输入是唤醒正文，不是唤醒次数；委派结果走 `subagent` 工具返回值，插件不查子级（子运行期间根回合未结束，守卫 ② 自然抑制唤醒，§7.6）。

## 7.6 分工模型（三层分工）

```
根 agent          规划「要点」：读状态 → 拆自足要点序列（子看不到根的会话历史）→
                  subagent（宿主原生一次性前台 run）委派一个子 → 调用等到子收尾，
                  收尾文本作为工具结果返回 ——判断归根，根不亲执
子 agent          串行执行要点：成功 → 下一个，不逐个回报；任一步失败 → 立即停止，
                  收尾文本写明现场（已完成 / 未完成 / 卡在哪）→ 正常收尾即结束
                  （一次性 run，不复用、不续发）
脚本（流程 §8）   点内的确定性步骤（提示符驱动 + 读应答 + 判据）；只做序列与判据，
                  不做决策、不自行重试；失败原样返回给子
```

**persona「分工协议」五条（根/子同读、按角色行事；纯书写约定，无代码解析）**

1. 根**规划要点**并委派；**判断归根，执行归子**，根不亲执。
2. 子**串行执行**要点；成功不逐个回报，**任一步失败立即停止**并写明现场。
3. **子是一次性 run**：一次委派 = 一次工具结果，子不被续用；有新要点由根**重新委派一个新的子**（每次都是全新上下文）。
4. 脚本管**点内步骤**、子 agent 管**点间顺序与执行智能**、根管**要点的产生与重写**，三者**互不越界**：子不重新规划、不擅自重试失败步骤。
5. **连接与登录是两个独立要点**：根已判定"已连接"时，子拿到的第一个要点就是"登录"（子不管 connect）；未连接时根把"连接"作为第一个要点。**判断归根，执行归子，脚本不猜**。

**委派模式（2026-10-03 裁定）**

| 项 | 现行口径 |
|---|---|
| 创建路径 | preset 行 `backgroundMode: one-shot` + `enableRunInBackground: false`（§7.1）：每次派发都是一次性 run——子的产出经**工具返回值**回注，不产生可继续子会话 |
| 不挂的控制工具 | `send_message` / `interrupt_agent` / `list_agents` **不注册**（只对可继续子有效）：旧子不可寻址，因而不存在"新委派落到旧子上下文"的通道 |
