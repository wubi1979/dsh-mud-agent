## §1 不变量

实现与测试都必须守住的十六条。违反时括号内是历史上真实发生过的症状。

| # | 不变量 | 症状 |
|---|---|---|
| **I1** | 用户 = 会话 = 运行时；**连接是会话无关的传输资源**，绑定方向单向（会话 → 连接） | 单槽位 `SID='console'`；切用户时 agent 被 dispose |
| **I2** | **agent 生命周期归官方**；插件只读解析（`ctx.agents.get`）并经官方原语投递：`followup`（无工具在途 → 新回合）/ `inject`（随在途工具结果进同回合；工具侧经 `exec.deferContext` 投递，§19.6.2）；**回合收束同样走官方原语 `exec.concludeTurn()`，且判据由流程驱动器给出**（B3，§19.6.2） | `agent "X" is already registered` → T1 全丢；运行时按投递尺寸推断终态 → 双权威（D8） |
| **I3** | **T2 是基线，T1 是唯一干预点**（`agent/request` + `prepend`，仅 lane=t1 换 provider） | 插件改写会话/全局模型、污染其他会话 |
| **I4** | **动作即契约**：规则/流程声明了动作，就必须有结局 —— **成功 / 失败 / 超时**三者之一（无"静默"）；"投递出去无人处理""命中未渲染""挂起无期限"都是缺陷，必须吵（error 日志 + diag 计数），不得静默等待或以 T2 重投兜底。**收口恒有界**：行流窗口必须显式声明收口（`settle`），`fallback` 到期恒以 `timeout` 结算（§19.1/§19.2） | 旧 `resolveLines` 失配 → 规则静默丢失；帧归属猜错 → 登录静默卡死；窗口无界 → 挂起无期限 |
| **I5** | **单流切分**：每条输入行在 session 里恰好出现一次、顺序不变（单一水位线记账 + 裁决器五站消费链的单遍结构，§5/§8.2）；**状态抓取与 `direct` 反射不消费行**（§19.7） | 同一段文本被 T1/T2 消息各投一次；折叠隐藏行 → span 空洞 |
| **I6** | **一个结算点 ≤ 一条投递消息**；**结算点 = 帧提交点**（§8.2 消费链站⑤投递视图）；standalone（帧内命中 / 人工回填 / 结算驱动 / 排队出队）是独立投递点，与结算点投递物理合流不算违反。同一回合内多条投递按到达顺序**逐步认领**，不制造两个决策者；**回合收束判据由流程驱动器给（B3），运行时不按投递尺寸推断**（§19.6.2） | T1 命令在途时 T2 又在旧状态上推理；运行时抢先收束仍在推进的流程 |
| **I7** | 规则语义只由**行序列 + 多行状态机**决定，与文本块/分包/截断无关 | 同一输出因网络节奏判类不同 |
| **I8** | 部署可变项一律 Config；**禁止模块级可变单例状态**（含匹配器上下文）；**T1 流程槽表归会话作用域**（adapter 保持无状态外壳，只按 `sessionId` 查表，§19.7 定案 8） | 多会话互相污染多行状态；T1 进程级单例持有会话状态 |
| **I9** | 任何丢弃 / 截断 / 失配都必须有 error 日志 + `/mud/diag` 计数 | "判类之后什么都没有" |
| **I10** | **单流程互斥**：同一会话同一时刻最多一个流程实例；流程激活期间**其它流程的入口一律不 arm**（判据不开，而不是"命中后忽略"）；期间出现的其它入口行记为 **pending entry**，当前流程结束后接续 | fullme 在 login 挂起期间启动 → 两条链争一个挂起槽 |
| **I11** | **流程单步的应答唯一性**：由在途窗口表的**窗口-步骤配对移交**（`windowSpecFor` 下发收口、`noteToolResult` 按 stepId 认领，§8.3/§19.3）保证 —— 同一回合里官方按工具调用顺序逐个 await 结算，**不另造挂起队列**；"同一回合至多一个在途工具"依赖官方缺省独占调度（`executionMode()` fail-closed：未声明 `isConcurrencySafe` → exclusive，§18 未决 #6）；直发命令不入窗口、受直发延后 gate 约束（§8.3）双保险；流程步的动作由 T1 **按槽逐条渲染**（§19.3），"本步命令的结算串掉别步"结构上不可能 | 第二条应答请求插进挂起槽 |
| **I12** | **直发延后 gate**（v0.9 W7.2 取代旧"挂起期闸门"）：窗口开启 ⇒ 直发命令延后到结算后再发（§8.3；`halt` 等高优先级豁免 —— 豁免只应服务打断路径，范围约束见 §18 未决 #8）；"先投递后唤醒"的顺序语义保留在推进路径上（§19.3：结算 → 驱动器复判 → 推进 stepId / 发布槽 → T1 渲染下一步） | 唤醒后步骤错乱；工具返回、loop 进下一步时收件箱里还没有动作 |
| **I13** | **收口与分类分离、注册期互斥**：**收口**（`settle`：inline / stream + 关闭触发 `on` + `fallback`）只回答"窗口何时关闭"；**分类**（`classify`：`ok`/`fail`/后继 `driver` 的自填正则）只回答"内容指向哪个 next" —— 二者正交、分属窗口与驱动器（§19.1/§19.3）；**声明才计 GA**（`on:{kind:'ga',count:N}`，隐式缺省废除）；**同一步骤的 `ok` 与 `fail` 判据集必须互斥、`driver` 不得与 `ok` 重叠**，装配期校验、违反即报错不装配；复判类序固定（retry → fail → 分支 → ok），类内多命中按声明顺序取首并留痕 | GA 与文本判据竞速 → 分支乱；ok/fail 写重叠 → 同一行两种结论；窗口替驱动器判类 → 收口与判据分歧 |
| **I14** | **打断按数字档位直接比大小**（`normal = 100`，见 §19）：规则声明 `interrupts`、流程声明 `priority`，`interrupts > priority` 才可打断；不可打断时该动作**排队**（不丢不串）；`login` = `1000`（不可打断） | 家务规则打断登录；或事件动作被无声丢弃 |
| **I15** | **T1 契约检验（T2 可用）**：规则 / 流程 / 工具 / 判据里**不得出现只有 T1 能理解的引用**（如 `turnRef` 式私有句柄）；投递消息必须自洽到"**T2 拿到同一条消息也能自己决定**"；**工具结果自洽**（v0.9 W7.3 扩展）：工具返回给模型的结果文本只描述"发生了什么 + 等到了什么"，不携带"下一步该怎么走"的私有指令（流程推进是 `noteToolResult` 内部行为，不进模型可见文本） | 机制退化成只服务 T1 的私有管道（"为开发流程管理器而开发"） |
| **I16** | **T1 私有状态不进 T2 可见面**（v0.11.0）：流程槽（`flowId`/`stepId`/`phase`/`captureSlots`/`retries`/`pendingCallId`）与流程词汇（`classify`/`captures`/`onSettle`）**一律不得进入投递消息、工具参数描述或工具结果文本**；模型可见面只剩收口 `settle`（§19.1/§19.3） | T1 状态化后把私有状态漏进模型面 → T2 看到无法解释的字段（破坏 I15） |

## §2 术语表

| 术语 | 定义 |
|---|---|
| **文本块（block）** | **网络层推送粒度**：由 `telnet` 的 `parsed` 事件发出，边界为 GA / EOR、300ms 静默刷出、断线收尾。是"一次服务端吐出的东西"（v0.6.0：300ms 静默只是**网络装配粒度**，不再是消费边界 —— 消费边界只认帧标记，§8.7） |
| **帧（frame）** | **消费/提交单位**（v0.6.0，§8）：行流裁决器以 GA/EOR（八成）与武装判据标记（十成）切帧，帧内存阀兜底防 OOM；状态抓取、规则触发、在途结算、流程行判据、投递都是帧提交的订户（§8.2 消费链），**不得自造边界** |
| **裁决器（行流裁决器）** | `SessionAdjudicator`（`deliver/adjudicator.ts`）：**唯一的边界裁决者** —— 行流缓冲 + 上述切帧 + 内存阀 + 五站消费链（§8.0–§8.2）；全部注册收口至唯一 `register(registration)` 入口（打断武装 / **流程入口 arm 与分支等待期布防的重放** / 直发判据投影，§8.5） |
| **行（line）** | 文本块经 `AnsiStreamParser` **行化**后的单位。感知层按行推进；语义上这些行仍属于它们来源的那个文本块（多行规则因此跨块、跨窗口都连续）。序列参数缓冲有界 `MAX_SEQUENCE_BUF = 64KB`（对照 telnet `MAX_SUB_NEG_LENGTH`），超限字节进丢弃态（W11.1⑤，§13） |
| **批次（batch）** | **投递给真实 LLM 的文本单位**（T2 路径专用）。由一个或多个文本块的行按单流切分组成，按 token 预算裁剪 |
| **规则命中（hit）** | 行级感知的命中记录：`{ ruleId, action, anchorAbs, data }`；`action` 是规则声明的确定性动作（一个工具调用） |
| **动作请求（action request）** | 投递给 T1 的消息所携带的"该做什么"：`{ tool, args }` + 来源规则 id。**与 T2 拿到的消息同形**（原文 + 动作），T2 拿到也能自行决定（I15） |
| **投递形态（原文投递 / 动作投递）** | 投递消息里**带不带原文**：**原文投递** = 触发段原文 + 动作请求（T1 规则命中 / 流程**入口**步动作，走 `segment[0..consumeTo]` 切分）；**动作投递** = 无原文可带（帧内命中 / 人工回填 / 结算驱动 / 排队出队），消息体只有动作请求。形态只决定"消息里有没有原文"，**与投递通道（`followup` / `defer`）正交**（§5、§19.6.2） |
| **消费边界（consumeTo）** | 最后一次命中的锚点行位置；决定"哪些行已由确定性规则消费" |
| **遗留段（carry）** | 消费边界之后、尚未决定的行；随下一次投递一起走（见 §5） |
| **单一水位线** | 每会话一条的**行流消费进度唯一记账**（v0.11.0 取代旧"交付水位/三水位"）。四类消费者推进它：规则/入口/分支命中行、流程 span（含兜底到期与打断提交区间）、T2 批次、仍带原文的投递；**状态抓取与 `direct` 不推进**（§5/§19.7） |
| **状态抓取桶** | state 规则的命中动作只有"抽取 → 同步 world"一个效果：**不推进水位、不折叠内容**；状态行保留在行流里作为普通行被后续 span/批次原样包含（v0.11.0 删除折叠机制，§4/§5） |
| **lane** | 一次投递的所有权标记：`t1`（T1 流程驱动器渲染）/ `t2`（真实 LLM 推理）；随消息的 `source` 走。**lane 只决定"这一回合谁来做"，不是两种世界** |
| **流程表（flow table）** | 装配期注册的只读声明：每条流程 = 有序**步骤**；每步 = `driver → action → settle/classify → next`（§19.1） |
| **步骤（step）** | 流程的一步：`driver`（进入判据）/ `action`（工具调用声明）/ `settle`（收口）/ `classify`·`next`（分类与后继）/ `captures`（抽取）/ `retry`（可选，步内重试）/ `timeoutMs`（步预算） |
| **驱动句（driver）** | 某一步的进入判据：服务端打出的提示行（如 `此ID档案已存在，请输入密码：`） |
| **收口（settle）** | 只回答"窗口何时关闭"的步级声明（`inline` / `stream` + 关闭触发 `on` + `fallback`）。**不解释内容** |
| **分类（classify）与复判** | 只回答"内容指向哪个 next"的步级声明（自填正则 + `onSettle`）。由**驱动器**在推进点（`noteToolResult`）对窗口带回的内容**走一遍**得出（`judgeStep`），类序固定 retry → fail → 分支 → ok |
| **形态 C** | 现行流程形态 = **收口器（窗口）+ 驱动器复判**：窗口净退化为纯收口器，判据由驱动器持有；收口触发从判据派生 ⇒ 二者不可能分歧（v0.10.14 定案，§19.2） |
| **关闭触发（closeOn）** | 窗口的提前关窗条件（`settle.on` 的正则或 `win-<n>:close` 标记命中）。命中即关窗且**不携带分类**（`settled:'evidence'`，与 `ga`/`eor` 同形不同名） |
| **流程槽（FlowSlot）** | 会话作用域的一格表：`{flowId, stepId, phase, render?, pendingCallId, retries, captureSlots}`。**T1 渲染下一步 tool-call 的唯一数据源**，也是 `callId ↔ 步骤` 的配对依据（§19.3） |
| **流程驱动器（T1）** | 有状态的流程执行者：拿工具结果 → 复判 → 查表决策 → 走下一步；输出面按槽渲染 tool-call。**与 T2 同构，区别只在决策来源**（LLM vs 流程表） |
| **触发器反射（direct）** | `action.direct: true`：命中规则即由运行时直发命令，**不属于收口/在途窗口/水位体系** —— 不开窗、不结算、不产生 span、不消费行；其应答按普通行进入后续消费批（§19.7 定案 5） |
| **在途窗口（in-flight window）** | v0.9 W7.2：一条发命令工具调用对应的应答窗口（id `w<seq>`）；**形态 C 下是纯收口器** —— 注册 → 发送武装 → 关闭触发命中 / N-GA 关窗 / 兜底到期 / abort / 断线 → 结算（只带回内容，§8.3）；直发命令不入窗口，受直发延后 gate 约束 |
| **挂起（suspend）** | 命令发出后等结果的状态：实现是**在途窗口表的一条在途窗口**（§8.3），结局由关闭触发 / N-GA / 兜底到期 / 打断 / 断线给出；旧"桥的一条 pending 应答"与挂起期闸门已删除（I12） |
| **唤醒/推进（advance）** | 窗口结算后由**驱动器复判**得出的单出口推进：命中分类 → 查表 → 更新槽 → 下一步；未命中 → 证据关闭按 `onSettle`、到期以 `timeout` 收束（§19.2/§19.3） |
| **打断（interrupt）** | 规则命中且档位高于流程时：把在途窗口结算为 `interrupted`、复位流程、可选发 `onInterrupt` 命令、事件动作经 followup 开新回合（§19.4） |
| **排队（pending action / pending entry）** | 不可打断时的事件动作 / 流程期间出现的其它流程入口：排队等流程结束，立即执行（不丢不串） |
| **分投器（delivery）** | L2 投递节拍（§5）的机制称谓：lane=t1 → 原文 + 动作请求投递；lane=t2 → 批次（token 预算裁剪 + `t2DeliverIntervalMs` 限流）；一个结算点 ≤ 一条投递消息（I6，standalone 为独立投递点）；defer/followup 投递通道在此择路（§19.6.2）；**回合收束判据由流程驱动器给（B3）** |
| **会话运行时** | `MudSessionRuntime`：一个 MUD 会话的全部游戏侧状态（连接绑定、感知、投递、在途窗口表、队列、world、回看缓冲（诊断）、**流程实例 + 流程槽**、定时器） |
| **预设（preset）** | 官方 agent 组合机制：`mud-player` 预设把 MUD 工具/人设/技能挂到原生 agent 上（见 §9） |

**已删除的概念**：Hit 积压、回合记录 / `turnRef`、帧归属（`activeTurnRef`）、搭车队列、`takeTurns` 游标（v0.4.0，§16）；**折叠行 / 折叠消费 / `deliveredAbs` 交付水位 / 三水位 / 发送水位 / 回看结算 / 历史查询（`mud_recall`）**（v0.11.0，§5/§19.7）；**判据-only 收口模型与"形态 A"脚手架（`closeForFlow` / `ReplySettle='flow'` / 窗口分类标记）**（v0.11.0，§8.3）；**N-GA 隐式缺省（`gaCount ?? cmds.length`）与 `WindowCriteria`/`gaOutcome`/`hit`/`hitText`**（v0.11.0，§8.3）；**投递尺寸推断的收束判据（判据 B）**（v0.11.0，§19.6.2）。

**数据流一句话**：`文本块 → 行 → 帧提交（§8.2 消费链：状态抓取 / 规则触发 / 在途结算 / 流程行判据 / 投递视图） → 投递消息（动作请求 或 批次） → 官方 agent 回合 → 工具调用 → 在途窗口（收口） → 驱动器复判 → 流程槽 → 下一步 tool-call`。

## §3 总体架构

```
入站逻辑行（telnet parsed: GA/EOR/300ms 静默装配/断线；游戏输出与工具应答同源）
      │                                  ← 唯一入口
      ▼
┌──────────────────────────────────────────────────────┐
│ 行流裁决器 SessionAdjudicator (v0.9 W7.1 §8, 分帧器并入) │
│   GA/EOR 八成 + 武装判据十成切帧; 内存阀兜底            │
└──────────────────────────────────────────────────────┘
      │ 帧提交 (消费链 §8.2, 单遍)
      ▼
┌──────────────────────────────────────────────────────┐
│ L1 行级感知  (每会话一实例，多行状态持久)              │
│   · 静态规则：state 桶抓取 → world（不消费行、不进 agent）│
│                event 桶命中 → 动作请求                 │
│   · 流程行判据：入口 arm（空闲）＋ 分支等待期布防         │
│                → 分支 / 打断 / 排队（本步判据随窗口走）   │
│   · 产出：动作请求[]{tool, args} + 消费边界 consumeTo   │
└──────────────────────────────────────────────────────┘
      │  行流 + 动作请求（会话私有）
      ▼
┌──────────────────────────────────────────────────────┐
│ L2 投递节拍  (每结算点一次判定；单流切分)               │
│   有动作 → T1 投递消息 = 原文 + 动作请求（流程仅入口步） │
│   无动作 → 批次 = segment（按 token 预算裁剪）           │
└──────────────────────────────────────────────────────┘
      │  agent.followup(mud-owned{lane, sessionId, 动作请求})
      ▼
┌──────────────────────────────────────────────────────┐
│ L3 选路  (官方 agent/request，prepend)                 │
│   lane=t1 → 拦截为 mud-t1；其余 → 不介入（T2 基线）     │
│   门: preset=mud-player（§9）或已绑定 MUD 会话          │
└──────────────────────────────────────────────────────┘
```
