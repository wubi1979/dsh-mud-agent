# T2 思考层：闭环、唤醒与 persona（§7–§9）

---

## §7 T2 闭环与三唤醒源

### 7.1 闭环

```
唤醒 → 组装上下文 → 思考（消化结算报告 / 目标 / 计划 / 学习）
     → 下发计划（要点 + 边界声明 + 相关技能与教训）
     → 子 agent 串行执行（引用技能/流程）
     → 结算即唤醒，报告回注会话
     → T2 消化该次结算并检视在途计划 → 经验教训沉淀
```

### 7.2 三个唤醒源

| 唤醒源 | 对应人的注意力回归 | 条件 |
|---|---|---|
| 静默到期 | 主动环顾——"没事且没事干" | **且无行流持有者、且上次结算已消化**（子级在跑 = 有事在干，不打扰） |
| 意识层危险唤醒 | 惊吓 | 立即，不等静默期；用**高置信判据**（死亡 / 断线 / 攻击）。**去重挂世界状态**（如"正在战斗"），**不挂行模式**（§6.2） |
| 子 agent 上报 | 下属汇报 | 受阻 / 完成 / 越界请示 / **异常终止（含预算耗尽）** |

- **源1 的守卫不能写成"无子 agent 在途"**：子 agent 目录里的空闲状态不代表任务完成（已结算的子级仍在目录里），据此判会让根在首次派单后永久认为"有事在干"；
- **双唤醒窗口**：子 agent 刚终结、结算唤醒还在排队时静默计时器恰好到期 → 根可能收到结算 + 静默两个唤醒。**无害，接受冗余唤醒**——T2 的决策输入是唤醒正文里的世界状态，不是唤醒次数；**不设"结算未消化"守卫**（为罕见冗余唤醒建状态子系统不值，I5）。

**越界不设第四个唤醒源**：HP 缓降、进入战斗这类无行可警的世界越界由意识层抓进工作记忆，**在静默到期的唤醒摘要里呈现**（§6.4、§9）——静默环顾本来就要带世界状态，越界事实搭这一次车。代价是"HP 开始跌"到"T2 知道"的延迟 = **静默期 ∪ 子级在途时长 ∪ 根阻塞期间**；遭攻击这类有行可警的场景仍走危险源立即唤醒。

### 7.3 唤醒器实现（wake.ts）——两源自建，结算源由宿主投递

```ts
class Wake {
  private silenceTimer                 // 有界静默 timer（形态参考 schedule/runtime.ts:194-201）
  private latch: string | null         // 危险去重：**挂世界状态**（如 inCombat），条件解除才重武装

  // 静默到期唤醒：静默 && 无行流持有者（"没事且没事干"）
  //   守卫写法见 7.2 两条 bullet（不写"无子 agent 在途"、不写"结算已消化"守卫）
  onSilence(): agent.followup(context.silence())     // followup: runtime-types.ts:222

  // 危险唤醒：steer 空闲自开回合、运行中步边界插话（runtime-types.ts:224-231, agent-loop/agent.ts:159）
  steer(d): agent.steer(context.danger(d))

  // 结算上报：宿主投递（continuation-activation.ts:881：idle→followup / running→steer）
  //   插件不重复唤醒，也不自报结算；**必须按 best-effort 理解**（§8）
}
```

## §8 结算即唤醒（检视是计划级），且唤醒是 best-effort

一步一请示是浪费——"异步"的确切含义是**要点级不打断**：计划执行中，子 agent 不为单个要点向 T2 请示，意外自行消化；只有受阻 / 完成 / 越界请示 / 异常终止四类结算才回到 T2。

**完成也唤醒**：子 agent 的结算通知会投递到父会话——父空闲则开新回合，父运行中则步边界插话，没有"只落日志、等自然醒"的第三态。因此：**结算即唤醒，检视是计划级的**——一次醒来消化该次结算并顺带检视在途计划。token 代价明码入账（§15：每份计划约 2 次 T2 调用 = 编制 + 结算检视）。

**但"唤醒"必须按 best-effort 理解**：宿主存在**四种不唤醒状态**，其中两种完全静默——① 子级首个 prompt 从未被接受；② 父不在注册表（丢弃且无日志）；③ 父正在关闭（转为持久但不唤醒的注入）；④ 投递抛错（仅记警告）。因此：

- **不承诺"必然送达"**；交付失败**无独立兜底机制**，由 §11 的预算路径承担（预算到期的"超时失败"本身就是一次结算，走同一通道回根）；
- 结算消息只含子级的**非空文本块**（无结构化输出通道），父要细节只能靠子级主动上报；书写格式用**固定文本约定**（RESULT / QUESTION / 本次新教训，§13），供根 T2 读文本消化——**不做代码解析**；
- 父运行中收到的结算**不丢失**，它在下一个步边界被消费（根阻塞在问人时会推迟到问人返回之后）。

## §9 唤醒上下文与 persona

### 9.1 上下文组装（context.ts，纯函数，瘦）

历史每请求自动携带（`agent-loop/src/agent.ts:631` + `deriveMessages()`）——计划、结算报告、技能调用都已在上下文里，**组装器不搬运历史**。每次唤醒正文只补两件模型看不到的东西：

```
buildWakeContext(reason) =
  [唤醒原因：事实短消息，不是指令]        // "静默环顾" / "危险：遭攻击（HP 18%，位置 茶室）" / 事实陈述
  [世界摘要：字段清单判据]              // 入选 = T2 本次决策必需：
                                       //   HP / 内力 / 位置 / 登录态 / 饥饿口渴 / 金钱
                                       //   + 越界事实（HP 缓降等搭静默这趟车）
                                       // 新增字段必须写理由——防孤儿字段
  [教训注入（第二期，lessons）]
```

- 计划**不单独建存储**：T2 输出计划 = assistant message 自然落会话日志；进度 = 结算报告（user message）。不建 plan 状态机、不建进度跟踪器（I8）；
- **compaction 是缺省挂载的**：缺省 profile 挂 `compaction-basic`（每个 `pre-step` 自动跑）+ 工具结果裁剪（>8192 字符裁成 4096+标记+1024），它按预算**重写会话面**。"历史全量携带"在缺省组合下不成立，⇒ **"计划被压缩后重注"是必需项**——但"计划被压缩导致失忆"目前**无例证，不建守护**（I5）；若实测出现，先考虑部署层关 compaction，再考虑重注机制（§19）；
- 克制原则：只给 T2 本次决策需要的；唤醒原因是**事实**（"HP 18%"），不是指令（"请逃跑"）。

### 9.2 persona（persona.ts，经 preset 行注册）

注册 `systemPrompt.section({name, order, text})`（**参数是对象**；组装走宿主 section 机制）——不自拼字符串进每次请求。**承载 = preset 行**（P2 D6 修订）：persona section 与三工具一起由 `src/preset.ts` 在 **preset 作用域注册一次，根与子级同见**（1.1-4 实测证实）；原「persona 只进根、子级身份纠正靠提示层」的方案作废——子级身份纠正由官方 `subagent:delegation` 运行时上下文承担（宿主 child-agent.ts 同款），本包不做提示层纠正。内容：

- 五层身份（你是玩家，下属替你跑腿）；
- **服务端拒绝是教育信号**（"你正忙着"这类占线应答说明活动没做完，先处理手里的活再重试——占线错误是天然的教育信号，处置归子 agent 的执行智能）；
- **子级在途时不得直接调 `mud_send`**（应走 `send_message`/`interrupt_agent`，牙齿见 §11）；
- 工具用法、计划格式（要点 + 边界声明 + 预算）；
- 维持类自查（口渴/饥饿/疲劳是要你规划的事）；
- **fullme 兜底常识**（第一期没有识别工具；问题上浮回到你这，你问人取码后带答案重入当前计划——[flows/fullme.md](../flows/fullme.md)）。

**禁令**：T2 唯一持有目标与意图连贯性；意识/反射不得替 T2 做计划级决策；无两执行者——子 agent 是计划执行半边。
