## §14 记忆三分与学习回路

| 类型 | 内容 | 技术承载 | 注入点 | 期次 |
|---|---|---|---|---|
| **工作记忆** | 世界当前状态（HP / 口渴 / 位置 / 登录态 / 金钱） | world.ts（意识层维护，I3） | 所有层读同一份 | 第一期 |
| **陈述记忆** | 经验教训（"那个店周三不开门"、"死后先捡尸体"） | lessons.json（上限 N 条，超限由 T2 归纳合并——人会遗忘，记忆会压缩） | 战略教训 → T2 唤醒上下文（§9.1）；战术教训 → **拼进子 agent 任务描述** | 第二期 |
| **程序记忆** | 技能与流程（"去茶室的走法"、login） | `skills/mud-<name>/SKILL.md` 人写种子 + flows/（§13）；宿主热加载、模型可见 | 计划编制引用、子 agent 执行调用 | 第一期种子；沉淀第二期 |

学习因此有双产物：**教训**（陈述，来自检视失败与意外）+ **技能**（程序，来自检视成功的要点沉淀）。

三条落地约束：

- **子级必须先能读到，才谈得上积累**：宿主只把技能**目录概要**注入根会话，子级看不到卷宗——相关技能/教训正文要**由根拼进子级任务描述**（`ctx.skills.get()` + `renderSkillContent()`；**没有**"把某技能注入某子 agent"的专用接口）；
- **教训回库第一期用文本约定**：子级结算末尾固定一节"本次新学到的教训"（§13.3），据此决定是否沉淀（宿主没有结构化输出通道）；
- 因此成本**随记忆积累下降**（不是"单调下降"）——前提是回库链路已通，否则每个子级都从零学起。

**技能沉淀的前置四条（装配期自检，否则静默失效）**：① 组合里真有技能工具（`tool-skill`；目录注入与根保留由它触发，子级本身不会触发）；② 沉淀走写/改工具（只有 `write`/`edit` 这两个工具名触发快速失效，其余依赖文件监听）；③ 会话有工作目录；④ 沉淀**低频批量**（每次目录变更都会在根历史追加一整份新目录副本，旧副本不被替换）。

沉淀（第二期）：成功要点 → SKILL.md 候选——T2 用宿主 write 工具写文件，**热加载与缓存失效宿主原生**，插件零接线。技能/流程对计划是**词汇**：编制时引用、执行时调用，无执行权。

## §15 成本账目

| 项 | 成本 | 说明 |
|---|---|---|
| 存在 / 反射 / 意识 | 0 | 代码 |
| T2 | 低频 × 单次贵 | 三源唤醒（§7）；**结算即唤醒**（§8）——要点级不请示，计划级必检视 |
| 子 agent | 每计划 1 次启动 + 若干次 × 上下文小 | **同模型下省的是上下文尺寸**：T2 上下文 = 全量历史 + 目标 + 计划（大），子级上下文 = 要点 + 状态 + 战术教训（小）。**结算唤醒 1 次/计划是固定成本**。模型降档（子级用便宜模型）只适用全新会话路线（spawn；继承历史的那条被固定为父模型以保缓存复用），二期实施 |
| 技能引用 | 0 | 已沉淀的要点执行近乎零思考 |

**上限主张按计划长度加条件**：主干含子 agent 后，"每步一次 T2 全量调用"变为"每计划一次编制 + 若干次小上下文子 agent + 1 次结算唤醒"——**长计划净省、短计划未必**（1–2 步的计划，子级冷启动 + 结算可能高于 T2 直跑）。因此：

- 上限主张**只对长计划成立**，须逐场景断言，恶化即回退；
- **短任务由 T2 直跑**（根持有全套工具，零额外开销）——这是正本清源的兜底，而不是"更小的子 agent"；
- 三条必须入账的事实：① 子级上下文是**额外支出**（自有系统提示 + 工具 schema + 历史），父在子级前台运行期间不重发自己的请求，但**每份结算在父空闲时开一个新回合**（N 次结算 = N 个回合）；② **续跑 ≠ 重跑**（前者重放整个子级历史且有多个失败先决条件，后者必得新 id、丢记忆）；③ 缺省挂 compaction，"历史全量携带"不成立（§9.1）；
- **验收必须量成本本身**：根上下文规模 / 每场景峰值 token（只数步数量的是正确性，不是成本，§17）。

## §16 观测与计数口径

### 16.1 行流语料（corpus.ts）

- **行流语料**：JSONL 全量落盘（时间戳 + 原文）——自有通道；**不进 Session**（`session.append` 是同步通知、高频行会拖账；自定义类型虽 log-only（`session/index.ts:720-724`），行级频率仍只落 JSONL）；
- **交换级事件（定案：只落自有 JSONL 通道，不进 Session）**：`mud/command-sent`、`mud/exchange-complete`（read 返回时）、`mud/danger-fired`（**命中即记**，不受 latch 门控——动作去重另算）、`mud/flow-result`。理由双重：① 凭据类发送在其中（login 的 name/pass），进 Session 有明文入账风险，JSONL 由 `sendCredential` 通道再减一层（凭据两条不落 command-sent）；② 频率虽低于行级，仍属诊断面，白名单外天然不进模型，落本地文件即可对账。

### 16.2 计数（写死，两个量）

- **决策点数 = `step/start` 数**（正确性护栏：**空续步 = 0**；每个进入的步一次，`types.ts:298-301`；`agent.ts:328`）。**注意偏差**：一步可含多次请求（重试走 `agent.ts:491 continue`，不新增 `step/start`），也可能零请求（`prepareRequest` 在 `:390` 抛错）；
- **实际调用数 = `assistant/message` ∪ `assistant/attempt`**（唯一持久的"结算过的尝试"对，每次尝试恰发两者之一，其和 = 尝试总数；失败于 `live.start()` 之前的尝试两者都不留；`session/src/types.ts:341-355`）；
- **重试/失败漂移 = 实际调用数 − 决策点数**（不是 message/attempt 两流之差）；
- **禁用 `request/header` 计数**：它只在该 loop 实例的首次请求（`initial`/`resume`）或 header 变化（`change`）或声明新 series（`series`）时发（`agent-loop/src/agent.ts:595-610`）——**不能**用来计数请求或决策点。没有任何 session 事件表示"请求真的发出去了"（只有进程内 `llm/stream` waterfall 或 `agent/assistant-stream` 的 start 帧）。
