## 2. 实质矛盾（必须处理）

### P1 交易类动作：权限静态 deny 与全链路验收直接冲突（两稿联合矛盾）★最高优先

- design4 §4.3："不可逆动作（交易、丢弃、交任务）**不在子 agent 权内**"；impl §3.5 据此写"pre-execute deny 交易/不可逆类工具（buy/sell/trade…）"——**字面是静态黑名单**。
- design4 §9 验收却要求"取钱 / 买食物"四行为**至少一次走"计划→子 agent→结算"全链路**——这两条行为必发 buy/withdraw 命令。按 impl 字面实现，验收**必然失败**。
- 根因：两稿都把"边界声明随计划自带"理解浅了。唯一自洽读法是 **deny 数据源 = 计划边界声明**：计划可显式放行特定交易（如"允许 buy 面包，预算 ≤X"），未授权时才默认 deny。
- 修复动作：
  1. design4 §4.3 补一句"除非计划显式授权"；
  2. impl 补**动态编译机制**——边界声明每计划不同，而 pre-execute 注册是装配时静态的；spawn 子 agent 时如何把本计划权限数据注入子会话作用域，impl 完全未写，是实现缺口。

### P2 同一权限域内两处拦截点分工不明（impl 内部）

- impl §3.5 工具面写"危险命令 denylist 一行判断直接返回错误（**工具内**）"，权限编译段又写"**pre-execute** deny 交易类"。
- 工具注册走 `agent/created` 一条路径覆盖根与子 agent——工具内 denylist **无法区分根/子**，一刀切会连根会话的 buy 也拦，违反"根放行"（design4 §4.3）。
- 修复动作：定案分工——对谁都拦的硬危险命令走工具内；计划边界（根放行、子受限）走子会话作用域的 pre-execute。
