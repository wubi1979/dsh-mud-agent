# 审计规约（可执行检查表）

- 状态：**规约（2026-09-25）**，供每轮代码审阅使用；与 `design4.md`/`design4-impl.md` 并列，只约束审阅方法，不改设计。
- 目的：把"自由发挥式审阅"换成**逐类固定核对**，消灭整类漏项与无据结论。
- 适用：`packages/mud-core2/` 下全部产物（`src/`、`test/`、`tsconfig*`、`package.json`）。

## 0. 证据分级（决定一条意见能不能提交）

| 级别 | 定义 | 处置 |
|---|---|---|
| **E1 静态事实** | 源码/配置可直接引用（带 `文件:行`） | 可提交为问题 |
| **E2 设计违背** | E1 + `design4*.md` 的明确条款（带 §号） | 可提交为问题 |
| **E3 实测事实** | 本机可执行命令的输出（typecheck / 测试 / 一次真实连接） | 可提交为问题 |
| **E4 推测** | 无 E1 支撑，仅"可能/大概" | **不许提交为问题**，只能作为"质疑"列出 |

硬规则：

1. **无证据不提交**：任何结论必须能给出 `文件:行`、`§` 或命令输出三者之一；
2. **不确知"不存在"**：判定"某文件/某字段/某分支不存在"前必须**先枚举**（glob/grep 全量），不得凭印象；
3. **路径类结论必须逐级写出解析**（`a/b → .. → ..`），不得靠格式判断；
4. **不把缓存产物当证据**（如 `node_modules/.vite/**/results.json`），运行结论一律现场跑；
5. **"没做"不等于"有问题"**：属于后续阶段/未接线的工作项计入"未落地"清单，不计为缺陷；
6. **同一事实只从一个来源取**，不叠加旧轮结论；每轮重新核对（代码在动）。

## 1. 检查类别（逐类过，不挑着看）

每类带**前置证据**：先跑该类的命令并留下输出，再下判断。没跑命令的类别一律记为"未执行"，不得用概述语气蒙混。

### C1 集合与映射完整性
- 每个白名单/黑名单/映射（`ATTR_LABELS`、`VITAL_FIELD`、`DANGER`、`REFLEX`、`DENY_HEADS`、`FLOWS`、工具参数 schema、分区表）是否覆盖其**定义域**？定义域在文档里（命令字段清单、流程步表、旧实现表）时逐项对照。
- 手法（须实际执行并列出命中）：`grep -n "new Set\(|Record<|readonly \[|readonly Flow" src`，再逐项写出"定义域来源 → 覆盖情况"。
- 反向检查同样必做：**设计要求的字段，代码里有没有写入点/消费点**（如 `session.loggedIn`、`vitals.hunger`），无写入点的记为问题或未落地。

### C2 外部 I/O 语义（send / abortWait / 回调）
- 每处出站动作（`mud.send`）与上行回调：**是否按设计去重、节流、或标注为未定**？逐处列出调用点与触发频率。
- 凭据类出站（`creds.name/pass`）额外核：**返回值/日志/session 事件里是否可能出现明文**（只看本次 read 返回的累积文本，不算模型上下文之外的历史）。
- 设计只规定"去重"而未规定"本层去重"的，计为**质疑**（见 §3），不计问题。
- 手法（须实际执行）：`grep -n "\.send\(|creds" src`，逐个回溯调用者与返回值来源。

### C3 状态生命周期
- 每个可变字段/状态：**谁写、谁清、有无孤儿**（写了没人读、置位没人复位）。
- 同时列出**一处状态两个表示**的情形（如闸门 `loggedIn` 与 `world.session.loggedIn`），指出权威方与同步点（缺同步点 = 问题或未落地）。
- 手法（须实际执行）：`grep -n "<字段名>" src` 全量，分别标注"写点/读点/复位点"；可变状态先枚举 `grep -n "private [a-z]|let " src`。

### C4 代码 ↔ 设计逐条对表
- `design4-impl` §3 的每条硬约束（判定序、吞触发行、latch 挂世界、禁两执行者、纯度纪律……）落到哪一行；未落地者记入"未落地"。
- 手法：按 §号逐条 grep 关键词，逐条给 `文件:行` 或"未落地"。

### C5 契约与边界
- 参数默认值与缺省语义；`undefined`/`null` 分支；同步抛 vs 异步 reject；断线/重连/复位路径；上界与溢出（缓冲、行数、超时）。
- 手法：读每个导出函数签名 + 其 `return` 分支，构造最小反例逐个核对。

### C6 测试有效性
- 断言是否可能**空跑成真**；是否依赖时序（固定 sleep、依赖单次 write 成批到达）；是否覆盖各分支；是否改共享表；是否有先红后绿。
- **先跑再判**：`vitest run` 只看结果不足以判定有效性，须逐条读断言。
- 手法：`grep -n "setTimeout\(|expect\(" test`，对照分支清单。

### C7 文档一致性
- 注释/文档字符串与实现是否互斥；同一事实是否两种措辞；待实测项是否显式标注。
- **范围写死**：本轮**改动的全部文件**（不是只看新增段落、不是只看自己写的注释），逐句对照实现；未改动文件的注释只在"与本轮改动直接相关"时才查。
- 手法：先 `git status`/文件行数变化确定改动清单，再对每个文件"注释句 → 实现行"成对列出；发现悬空引用（注释提到不存在的常量/函数）即记问题。

## 2. 输出格式（结论固定写法）

```
## 本轮执行情况（逐类，先列这个）
| 类 | 执行的动作（命令/枚举） | 结果 |
|---|---|---|
| C1 | <命令> | <命中与对表结论，或"未执行"> |
| ... | | |

## 通过项（本轮复核）
- <事实>（文件:行）

## 问题（E1/E2/E3）
**N. <一句话标题>**
证据：<文件:行 / § / 命令输出>
修复：<一句话>

## 质疑（E4，不计为问题）
- <一句话疑问 + 为什么值得问>

## 未落地（不计为缺陷）
- <设计要求的机制，尚未接线/未实现>

## 待实测（不阻塞）
- <需真实语料或真实连接才能定的刻度>
```

`## 本轮执行情况` 表是**强制项**：每类必须有一行，未执行的写"未执行"并说明理由。缺此表的结论视为不合规，可直接退回。

## 3. 质疑的写法

质疑**只用来提问**，不夹带结论、不要求改。判据：若一条意见去掉"我认为应该"之后剩下的事实不足以说明它是错的，它就该是质疑。

## 4. 可重复执行的证据命令

```powershell

pnpm exec tsc -p tsconfig.test.json          # 期望退出码 0

# 测试

# 产物清单（判定"不存在"前必须先跑）
Get-ChildItem -Recurse -File -Include *.ts src,test
```
